01

What this project is actually trying to do

In one line: build the first open-source, Python-native ML model that predicts peak inter-story drift ratio (PIDR) for reinforced-concrete moment frames designed to BNBC 2020, trained on OpenSeesPy incremental dynamic analysis (IDA) data across all four of Bangladesh's seismic zones — then use that same dataset to compare four framing systems (Non-Sway, OMRF, IMRF, SMRF) and find where extra ductility detailing stops paying for itself.

Six research objectives

  1. 01

    Build parametric RC frame models, 5–15 storeys, coded to BNBC 2020.

  2. 02

    Run IDA with scaled ground motions to generate a large seismic-response dataset.

  3. 03

    Train and benchmark four ML families — linear regression, random forest, XGBoost, ANN — against each other for PIDR prediction.

  4. 04

    Derive fragility curves at Immediate Occupancy, Life Safety and Collapse Prevention.

  5. 05

    Use SHAP to find which structural and seismic parameters actually drive drift.

  6. 06

    Compare Non-Sway / OMRF / IMRF / SMRF to locate the cost-vs-performance "sweet spot" across all four zones.

Six questions the paper has to answer

  1. Q1

    Can ML models hit R² > 0.90 predicting PIDR from structural + seismic features?

  2. Q2

    Which features — period, zone, soil class, height — matter most?

  3. Q3

    How do fragility curves differ across zones (Z = 0.12 to 0.36)?

  4. Q4

    Does building height or the zone coefficient dominate drift response?

  5. Q5

    What's the performance gradient between the four framework types, by height?

  6. Q6

    Which framework is the optimal pick, balancing complexity against performance, per zone?

03

Reality check — verify before you trust

The repo's own documents describe Phase 1 and Phase 2 as "100% complete" and Phase 3 as "production ready." Reading all of them side by side tells a more specific story: the code and scaffolding are genuinely thorough, but as of the most recent dated entry (22 Apr 2026), the actual 8–12 hour compute campaign that produces real data had not been run yet — and everything downstream of it is illustrative. These six items are worth 20 minutes each before you plan around any number in the repo, including the ones on this page.

Highest priority

The pipeline has a silent "demo mode"

If OpenSeesPy isn't actually importable in the execution environment, the campaign script doesn't fail — it substitutes synthetic placeholder data and calls this "OK." Run the full pipeline in an environment where OpenSeesPy is broken or missing, and you can end up with a complete-looking 51,200-row CSV, trained models, R² scores and plots that contain zero real structural physics.

Source: START_HERE.md, "OpenSeesPy not available (Demo Mode)" note. Action: before trusting any output, run python -c "import openseespy.opensees as ops; ops.wipe(); print('OK')" yourself, in the exact environment that will run the campaign, and confirm it prints OK — not just that the pipeline "completed."

Nothing downstream is real yet

Phase 3's own performance numbers are labelled "typical," not measured

The Phase 3 ML delivery doc presents a full model-comparison table (XGBoost test R² ≈ 0.81, etc.) under the heading "Expected Performance (Typical Results)" — before Phase 2's real dataset existed. It's a plausibility sketch, not a result. Treat every number in the repo as a placeholder until you've regenerated it yourself from real IDA output.

Source: PHASE3_COMPLETE_DELIVERY.md vs. FINAL_STATUS_REPORT.md (both dated 22 Apr 2026 — the latter still lists the campaign as the "next action").

Internal conflict

The Life Safety drift threshold disagrees with itself

The README's fragility framework sets Life Safety at PIDR = 2.0%. The project status doc's Phase 4 success criteria list Life Safety at < 2.5%. A 25% difference in the LS threshold changes every fragility curve and every "P(LS | Sa)" number in the eventual paper.

Source: README.md §3.3 vs. PROJECT_STATUS.md, Phase 4 deliverables. Action: pick one value, record why, and hard-code it once in config/bnbc_parameters.yaml rather than leaving two numbers live in two documents.

Internal conflict

Even the target journal's impact factor disagrees with itself

The README lists Buildings (MDPI) at IF 3.1; the project status doc lists 3.8. Neither may be current — Buildings is presently ranked Q2 in Engineering (Civil) and Q1 in Architecture, with the article processing charge risen to roughly 2,600 CHF (the README's ~1,800 CHF estimate is stale) and a median first-decision time near 15 days as of 2026. Small thing, but it's a clean example of why nothing in these documents should be cited into the actual paper without re-checking it live.

Source: README.md §2.3 vs. PROJECT_STATUS.md executive summary, cross-checked against mdpi.com/journal/buildings on 06 Aug 2026.

Scope grew — re-time before committing

The dataset target roughly quintupled between the original plan and the built infrastructure

The README's original Phase 4/execution-plan math (5 buildings × 500 GMs × 4 zones, trimmed to non-collapse runs) targets ~7,500–10,000 records. The infrastructure that actually got built targets 80 buildings × 32–40 verified records × 16 levels ≈ 51,200 — almost certainly because the four-framework comparison got folded into the core matrix rather than staying a side study. That's a reasonable evolution, but it means the "8–12 hours" compute estimate deserves a timed pilot run on your own hardware before you block out a day around it.

Source: README.md §4 Phase 5, §7.3 vs. FINAL_STATUS_REPORT.md campaign configuration.

Sets expectations

The stated success target and the illustrative result don't match

Success criteria call for the best model to reach R² ≥ 0.90 on held-out data. The same document's own "typical results" table shows its best illustrative model — XGBoost — landing at R² ≈ 0.81. Treat 0.90 as aspirational. A well-argued 0.80–0.85 with honest discussion of why is a publishable, defensible result; chasing 0.90 by overfitting feature engineering to the test set is not.

Source: PROJECT_STATUS.md, Phase 3 success criteria vs. PHASE3_COMPLETE_DELIVERY.md, expected performance table.
